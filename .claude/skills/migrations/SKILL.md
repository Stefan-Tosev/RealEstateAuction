# Changing the schema

`prisma/schema.prisma` is one-to-one with `docs/architecture.md` §2.
A schema change that the architecture doc does not describe is either a
doc that needs updating or a change that needs rethinking — decide which
before writing the migration.

## The loop

```bash
npm run db:migrate      # prisma migrate dev — authors and applies
npm run db:generate     # regenerate the client if the types look stale
npm test                # the unit suite reads the generated types
```

`migrate dev` prompts for a migration name. Give it snake_case describing
the *change*, not the ticket: `rate_limit_hits`, `bid_increment_bands`,
`fee_vat_split`.

Postgres must be up — `docker compose up -d`, then `start.cmd` for the
whole stack. A migration that fails with P1001 has not partially applied;
it has not run at all, and the safe move is to bring the database up and
rerun rather than to hand-edit anything.

**Never leave the tree with a changed `schema.prisma` and no applied
migration.** The generated client then describes a database that does not
exist, every test that touches Prisma fails, and the failures point
everywhere except at the cause. If the database is unreachable, revert
the schema edit and come back to it.

## Applying in production

```bash
npx prisma migrate deploy
```

Never `migrate dev` on a server — it tries to author migrations and
prompts for a name, so it hangs forever. `deploy/deploy.sh` already does
this in the right place: after the build, with the worker stopped, before
the app restarts. See the `deploy` skill.

## Conventions this schema keeps

Break one and the migration will work while the codebase stops being
uniform, which is worse than an error.

- **snake_case in the database, camelCase in Prisma.** Every field carries
  `@map`, every model `@@map`. `hitAt DateTime @map("hit_at")`.
- **Ids are generated by the application, not the database.** No
  `DEFAULT` on an id column. Two hand-written migrations broke this and
  had to be reconciled — see `20260807140000_schema_drift`.
- **Money is `BigInt` minor units**, column named `*_minor`, and **must
  not have a default**. `vat_minor DEFAULT 0` meant an insert that omitted
  the ДДС silently recorded zero tax; that default was dropped
  deliberately. Adding a NOT NULL money column to a populated table needs
  a backfill, not a default left behind.
- **Timestamps are `@db.Timestamptz(6)`.** Never bare `timestamp`.
- **`citext` for anything compared case-insensitively** — email, chiefly.
  The extension is declared in the datasource block; on a fresh server it
  must be created by a superuser before the first migration runs.
- **Indexes go in the schema**, so they are part of the migration, not
  something applied by hand and lost on the next machine.

## Two things Prisma will get wrong on its own

**Optional relations get `ON DELETE SET NULL`.** For `outbox` that
violates the `outbox_one_recipient` check constraint — nulling both
recipient columns means erasing a user fails on a constraint. It cascades
instead, which is also right on its own terms: a queued message to
somebody who no longer exists has nowhere to go. Check the generated SQL
for any relation where null is not a legal state.

**`bids` is append-only by trigger.** Nothing in the application can
update or delete a bid, and that is `docs/architecture.md` §3. A
migration touching that table has to account for the trigger, and a row
leaked into it by a test cannot be tidied by hand afterwards.

## Drift

Drift is silent until somebody regenerates a migration and gets a diff
nobody expected. `20260807140000_schema_drift` exists because of exactly
that, and its SQL is commented with what each reconciliation was for —
read it before writing a similar one.

To check: `npx prisma migrate status`, and `npx prisma migrate diff` to
see what the database and the schema disagree about. Reconcile with a
real migration that has a name and comments. Never with a manual `psql`
statement — that fixes this machine and leaves every other one wrong.

## After the migration

- `npm run db:seed` is idempotent and refreshes relative dates; run it if
  the change affects seeded data.
- `npm run check:clean` asserts the database is as the seed left it —
  useful after a migration that touched rows.
- A new enum value is a **compile error waiting to happen** in the good
  way: `LotStatus` is used in exhaustive `Record<LotStatus, …>` maps
  (`src/server/catalogue/publish.ts`) so that adding a status forces every
  decision about it to be made. Run `npm run typecheck` and answer what it
  asks rather than widening the map's type.
